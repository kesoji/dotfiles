# 観点別レビュアー(ユーザーレベル)

どのリポジトリでも使える汎用版。あるプロジェクトの `.claude/agents` を元に、環境固有の前提を
「各リポジトリの CLAUDE.md と規約から集める」形に置き換えた。

1人で開発していると、調べる人と疑う人が同じになる。同じ頭からは、聞いたことしか出てこない。
プロダクト開発の役割分担を持ち込んで、**反対側だけを担当する常設のレビュアー**を置く。
全員「本当か」「どこまでか」「まだ有効か」しか言わない。「やろう」と言う担当は1人もいない。

## 招集は `/review-gate` が行う

**レビュアーを直接呼ばない。** 進行役スキル `/review-gate`(`~/.agents/skills/review-gate`)が
招集し、結果を1枚の決裁書に畳んで返す。人間が読むのは常にその1枚。

| ゲート | 起動 | 招集される担当 |
| --- | --- | --- |
| 着手前 | `/review-gate issue <N>` | `pm-critic` / `customer-advocate` |
| PR前 | `/review-gate pr` | `sre-reviewer` / `security-reviewer` / `qa-reviewer` / `ux-designer` |

## プロジェクト版との関係

同じ名前のエージェントがプロジェクト(`.claude/agents/`)にあれば、そちらが優先される。
環境固有の前提(本番の制約、ドメイン用語、テナント境界の名前など)を書き込みたいリポジトリでは、
同名のエージェントをプロジェクトに置けば、このユーザー版を上書きできる。

## 前提の集め方(全担当共通)

ユーザー版はリポジトリ固有の知識を持たない。毎回、次の順に読んでから判定する。

1. リポジトリのルートと、差分が触るディレクトリの `CLAUDE.md`
2. `CLAUDE.md` から辿れるレビュー観点・規約・設計資料(例: `docs/reviews/`、`docs/standards/`、`docs/specs/`)
3. 自分の担当に関係するものだけを読む。全部を読まない

読んだ資料に書かれていない前提を、推測で作らない。

## 原則

1. **決めるのは人間。** レビュアーは材料を出すだけで、issue のクローズもラベル変更も
   マージもしない。`/review-gate` も推奨を出すだけ。
2. **書き込みはプロンプトで禁止している。** 6体とも `Edit` / `Write` を持たないが、`Bash` は持つ
   (`gh` / `git diff` を使うため)。禁止はプロンプトへの信頼に依っており、ツールで保証されてはいない。
3. **黙れることを保証する。** `指摘なし。` `対象外。` は正常動作。毎回何か返すレビュアーは指摘の価値をゼロにする。

## 追加するときの型

1. **役割** — 何だけを見るか。1文で
2. **見るもの** — 何を根拠にしてよいか
3. **チェックすること** — 具体的な問いのリスト
4. **やらないこと** — 特に「他の担当の領分」を明示する
5. **黙るべきとき** — どういう条件なら `指摘なし。` を返すか
